# รายงานตรวจสอบ Admin CMS — Sanpudam 168

วันที่ตรวจ: 19 ตุลาคม 2569 (Asia/Bangkok)  
ระบบเดิม: https://sanpudam168.1d1d.workers.dev/admin/#/  
ระบบเป้าหมาย: Next.js App Router, JavaScript, Tailwind CSS, MongoDB Atlas, Cloudinary และ Auth.js

## 1. ขอบเขตและความน่าเชื่อถือ

ตรวจผ่าน Cloud Browser หลังผู้ใช้ลงชื่อเข้าใช้ผ่านช่องทางปลอดภัย สำรวจทุกเมนูใน Sidebar หน้ารายการ ฟอร์มสร้างของทุกโมดูลเนื้อหา ฟอร์มแก้ไขข่าวและสิ่งศักดิ์สิทธิ์/วัตถุมงคล รวมถึงฟอร์มข้อมูลส่วนกลางที่เปิดแก้ไขได้ทันที

ไม่ได้บันทึก ลบ อัปโหลด เปลี่ยนการตั้งค่า เปลี่ยนรหัสผ่าน หรือส่งออกข้อมูลใด ๆ การลงชื่อเข้าใช้ตามที่ได้รับอนุญาตทำให้ระบบบันทึกเหตุการณ์เข้าสู่ระบบตามปกติ ไม่ได้เปิดอ่านค่ารหัสผ่านหรือข้อมูลลับ ไม่ได้เปิดรายละเอียดผู้ส่งข้อความ รายงานไม่คัดลอกข้อมูลติดต่อส่วนบุคคลหรือค่าการตลาด

คำว่า “พบ” หมายถึงเห็นใน UI; ความสามารถบันทึก/ลบ/อัปโหลดเป็นการยืนยันว่ามีตัวควบคุม ไม่ใช่ผลทดสอบการทำงานจริง ยังไม่ตรวจฐานข้อมูล โค้ด API สิทธิ์ฝั่งเซิร์ฟเวอร์ หรือโครงสร้างจัดเก็บไฟล์ ข้อเสนอด้านสถาปัตยกรรมเป็นแบบออกแบบใหม่ ไม่ใช่ข้อยืนยันระบบภายในเดิม

## 2. สรุปผู้บริหาร

CMS เดิมครอบคลุมงานเนื้อหาเว็บไซต์ได้ค่อนข้างครบ ไม่ใช่เพียงข่าวและแกลเลอรี แต่มี singleton สำหรับข้อมูลศาลและหน้าประวัติศาล ระบบข้อมูลตัวอย่างระดับฟิลด์ การตรวจสุขภาพเว็บ และประวัติแก้ไขพร้อมค่าก่อน/หลัง

สิ่งที่ควรรักษา: ภาษาไทยเข้าใจง่าย, ตัวนับจำนวนอักษร, SEO รายเนื้อหา, alt text, การจัดลำดับด้วยลากและลูกศร, จุดโฟกัสแบนเนอร์บนมือถือ, อัปโหลดหลายภาพ, preview, ลิงก์ดูบนเว็บ และการตรวจความพร้อมของเนื้อหา

ประเด็นสำคัญก่อนย้าย: มีข้อมูลตัวอย่าง 32 ฟิลด์ใน 16 รายการ; วิดีโอ 1 รายการยังขาดไฟล์; ไม่พบเครื่องมือส่งออกใน UI ที่ตรวจ; ช่องหมวดหมู่ของวัตถุมงคลแสดงเพียง “— เลือก —” ทั้งฟอร์มใหม่และฟอร์มเดิม แม้หน้าหมวดหมู่มี 3 รายการ ต้องตรวจ mapping หรือการโหลดตัวเลือกก่อนย้ายจริง

## 4. Dashboard และหน้ารายการ

Dashboard มีคำทักทาย ป้ายเตือน 32 จุด ทางลัดข่าว 3 ข่าว แกลเลอรี 10 ภาพ แบนเนอร์ 4 ภาพ และข้อมูลติดต่อ พร้อมรายการแก้ไขล่าสุดและลิงก์ดูประวัติทั้งหมด ไม่พบสถิติ traffic หรือ approval workflow ในหน้านี้

หน้ารายการเนื้อหามีค้นหา เลือกทั้งหมด checkbox รายรายการ ลิงก์เพิ่ม และลิงก์เข้าแก้ไข พร้อมจำนวนรวม ข่าวเรียงวันที่ล่าสุดก่อน ส่วนแกลเลอรี แบนเนอร์ sacred หมวดหมู่ วิดีโอ รีวิว FAQ และทีมงาน มีคำแนะนำลากจุด 6 จุดหรือใช้ลูกศรจัดลำดับ รูปแกลเลอรีแสดงขนาดพิกเซล รายการบางประเภทแสดงสถานะข้อมูลตัวอย่าง และ FAQ แสดงป้าย “แสดงในหน้าแรกด้วย”

ไม่ได้เลือก checkbox เพื่อเรียก bulk action จึงยังไม่ยืนยันชื่อและขอบเขตคำสั่งแบบกลุ่ม ไม่ได้ทดลองเปลี่ยนลำดับ เพราะอาจบันทึกทันที

## 5. พจนานุกรมฟิลด์

เครื่องหมาย * คือ UI ระบุว่าบังคับ ตัวเลขในวงเล็บคือเพดานอักษรที่ UI แสดง ไม่ใช่การทดสอบ validation ฝั่งเซิร์ฟเวอร์ ชื่อ key ภาษาอังกฤษเป็นข้อเสนอสำหรับระบบใหม่

### 5.1 ข่าวสารและกิจกรรม — `news`

| ฟิลด์ | รูปแบบ / ข้อกำหนด | key ที่เสนอ |
|---|---|---|
| หัวข้อข่าว* | ข้อความ 120 | title |
| ชื่อในลิงก์ (ภาษาอังกฤษ)* | slug | slug |
| วันที่* | date picker | date |
| รูปปก* | ภาพ คงสัดส่วนเดิมหรือครอปเอง | coverMediaId |
| คำอธิบายรูป | alt text | coverAlt |
| สรุปสั้น (แสดงบนการ์ด)* | textarea 220 | excerpt |
| เนื้อหาข่าว* | textarea 15,000; บรรทัดว่างขึ้นย่อหน้า, **ข้อความ** เป็นตัวหนา | body |
| รูปเพิ่มเติม | array ของรูปบังคับต่อแถวและ alt; เพิ่ม/ลบแถว/เลื่อนขึ้นลง | images[] |
| หัวข้อสำหรับ Google | ไม่บังคับ 60 | seo.title |
| คำอธิบายสำหรับ Google | ไม่บังคับ 155 | seo.description |
| แสดงบนเว็บ | boolean | isPublished |

ฟอร์มเดิมมีแก้ไขล่าสุด ดูบนเว็บ ดูตัวอย่าง บันทึก ประวัติรายการ และปุ่มลบรายการ ไม่พบระบบ tags, author editor, กำหนดเวลาเผยแพร่ หรือ pin ข่าวในฟอร์มที่ตรวจ

### 5.2 สิ่งศักดิ์สิทธิ์และวัตถุมงคล — `sacredItems`

| ฟิลด์ | รูปแบบ / ข้อกำหนด | key ที่เสนอ |
|---|---|---|
| ชื่อ* | ข้อความ 80 | name |
| ชื่อในลิงก์ (ภาษาอังกฤษ)* | slug | slug |
| หมวดหมู่* | select; ไม่โหลดตัวเลือกในหน้าที่ตรวจ | categoryId |
| ประเภท* | สิ่งศักดิ์สิทธิ์ภายในศาล / วัตถุมงคล (สอบถาม/สั่งจองทางไลน์) | type |
| รูปหลัก* + คำอธิบายรูป | ภาพและ alt | primaryMediaId, primaryAlt |
| คำอธิบายสั้น* | 220 | excerpt |
| รายละเอียด | textarea 8,000; รูปแบบย่อหน้าและตัวหนา | body |

| รุ่น/เนื้อ | array: ชื่อเนื้อ/รุ่น* 60, จำนวนจัดสร้าง, หมายเหตุ 60 | variants[] |
| SEO | title 60, description 155 | seo |
| แสดงบนเว็บ | boolean | isPublished |

ตัวอย่างวัตถุมงคลที่ตรวจมีรุ่น/เนื้อ 8 แถว มีปุ่มบันทึก ลบ และประวัติ ไม่มีหลักฐานระบบตะกร้า checkout payment stock หรือ order; การสอบถาม/สั่งจองเชื่อมกับ LINE

### 5.3 แกลเลอรี — `galleryItems`

รูป* (`mediaId`), alt (`alt`), คำบรรยายใต้รูป 120 (`caption`), แสดงบนเว็บ (`isPublished`) และลำดับ (`sortOrder` ที่เสนอ) รูปคงสัดส่วนเดิมหรือครอปเอง หน้ารายการมีปุ่มอัปโหลดหลายรูป แต่ไม่ได้เปิดเลือกไฟล์หรือทดสอบ upload จึงยังไม่ยืนยัน limit จำนวน/ขนาดไฟล์ และลำดับการตั้ง caption ระหว่าง batch upload

### 5.4 แบนเนอร์หน้าแรก — `banners`

รูปแบนเนอร์* สัดส่วน 3:2 แนวนอน, alt, คำบรรยายสั้นบนภาพ* 40 และแสดงบนเว็บ มีจุดสำคัญสีทองที่เลือกบนภาพเพื่อป้องกันจุดนั้นถูกตัดบนมือถือ พร้อมการจัดลำดับรายการ

เสนอ `mediaId`, `alt`, `caption`, `focalPoint:{x,y}`, `isPublished`, `sortOrder` ไม่พบช่องลิงก์ปลายทาง CTA ช่วงเวลาเริ่ม/สิ้นสุด หรือภาพ mobile แยกในฟอร์มที่ตรวจ

### 5.5 หมวดหมู่ — `categories`

ชื่อหมวด* 40 (`name`), slug* (`slug`), คำอธิบายหมวด 300 (`description`), แสดงบนเว็บ (`isPublished`), ลำดับ (`sortOrder`) มี 3 หมวดจริงในรายการ แต่ความเชื่อมโยงกับ select ใน sacred ต้องตรวจเพิ่ม

### 5.6 วิดีโอแนะนำ — `videos`

ชื่อวิดีโอ* 80 (`title`), ไฟล์วิดีโอ MP4* ไม่เกิน 90 MB (`videoMediaId`), ภาพปกอัตโนมัติหรือเลือกเอง (`posterMediaId`, `posterMode` ที่เสนอ), คำอธิบาย 300 (`description`), แสดงบนเว็บ และลำดับ ไม่พบช่อง YouTube URL ในฟอร์มนี้; ลิงก์ช่อง YouTube อยู่ใน Settings ซึ่งเป็นคนละหน้าที่

### 5.7 รีวิว — `reviews`

ชื่อผู้รีวิว* 40 (`displayName`), อาชีพ/ที่มา 60 (`sourceLabel`), ข้อความรีวิว* 500 (`quote`), คะแนน 1–5 (`rating`), แสดงบนเว็บ และลำดับ ไม่พบฟิลด์รูปผู้รีวิวหรือระบบนำเข้ารีวิวจากแพลตฟอร์มภายนอก

### 5.8 FAQ — `faqs`

คำถาม* 140 (`question`), คำตอบ* 800 (`answer`), แสดงในหน้าแรกด้วย (`showOnHome`), แสดงบนเว็บ และลำดับ UI แนะนำให้เขียนคำถามแบบที่คนค้นหา และประโยคแรกของคำตอบควรตอบตรงประเด็นในตัวเอง

### 5.9 ทีมงานผู้ดูแลศาล — `teamMembers`

ชื่อ* 60 (`name`), ตำแหน่ง/หน้าที่* 60 (`roleTitle`), รูปไม่บังคับ สัดส่วน 1:1 (`photoMediaId`), alt, แนะนำตัวสั้น ๆ 300 (`bio`), แสดงบนเว็บ และลำดับ ไม่พบช่องบัญชีผู้ใช้หรือสิทธิ์ CMS; บุคลากรที่แสดงหน้าเว็บไม่ควรถูกตีความเป็น admin account

### 5.10 เนื้อหาหน้าประวัติศาล — `aboutPage` (singleton)

|---|---|
| หัวข้อประวัติ* | 80 |

| ประวัติความเป็นมา* | long text 8,000 |
| รูปประกอบประวัติ + alt | คงสัดส่วนเดิมหรือครอป |

## 7. Media และตัวเลือกส่งออก

สิ่งที่เห็น: เลือกรูป/เปลี่ยนรูป, ขนาดพิกเซล, สัดส่วนที่แนะนำ, crop ตามคำอธิบาย UI, alt text, เอารูปออกในช่องที่ไม่บังคับ, focal point ของ banner, gallery multi-upload, video MP4 90 MB และเลือก poster เอง/อัตโนมัติ

สิ่งที่ยังไม่ยืนยัน: รูปแบบไฟล์ภาพที่อนุญาต ขนาดสูงสุด การบีบอัด EXIF การอัปซ้ำ ความคืบหน้า retry crop dialog จริง การใช้ media library กลาง การลบไฟล์เมื่อเลิกใช้งาน และ provider ของระบบเดิม เพราะไม่ได้เปิดเลือกไฟล์หรืออัปโหลด

ไม่พบปุ่ม Export CSV/JSON, backup, download originals หรือ export media ใน Dashboard, หน้ารายการ, ฟอร์มเนื้อหา, Settings และเมนูดูแลเว็บที่ตรวจ ไม่ได้แปลว่า backend ไม่มีความสามารถนี้ ต้องสอบถามผู้ดูแลระบบเดิมหรือผู้พัฒนา ไม่ได้เรียก endpoint แฝงหรือดึงฐานข้อมูล และไม่ได้ส่งออกข้อมูลส่วนบุคคล

## 9. MongoDB Atlas ที่เสนอ

| Collection | ข้อมูลหลัก / ความสัมพันธ์ |
|---|---|
| `siteSettings` | singleton ใช้ `_id` คงที่; identity/contact/hours/social/contactTopics/OG/analytics |
| `pages` | singleton `_id:about`; sections และ embedded arrays ของตรา/พร/ขั้นตอน |
| `categories` | name, slug, description, isPublished, sortOrder |
| `sacredItems` | categoryId → categories; type, body, variants[], media references, SEO |
| `news` | title, slug, date, excerpt, body, cover และ ordered images[], SEO |
| `galleryItems` | mediaId, alt/caption, sortOrder, isPublished |
| `banners` | mediaId, caption, alt, focalPoint, sortOrder, isPublished |
| `videos` | videoMediaId, posterMediaId, posterMode, title, description, sortOrder |
| `reviews` | displayName, sourceLabel, quote, rating, sortOrder, isPublished |
| `faqs` | question, answer, showOnHome, sortOrder, isPublished |
| `teamMembers` | name, roleTitle, bio, photoMediaId, sortOrder, isPublished |
| `mediaAssets` | Cloudinary metadata + legacy mapping + usage references |
| `contactMessages` | collection แยกสิทธิ์; schema รอยืนยันจากระบบรับข้อความจริง |
| `auditLogs` | actorId, action, entityType/entityId, field changes แบบ redact, createdAt |
| `users` และ auth storage ที่จำเป็น | ตัวตนและสิทธิ์ตามการเลือกกลยุทธ์ Auth.js; ไม่ใช้ teamMembers แทนผู้ดูแล |

ฟิลด์ร่วมที่เสนอ: `legacyId`, `isPublished`, `sortOrder` เมื่อเกี่ยวข้อง, `createdAt`, `updatedAt`, `createdBy`, `updatedBy`, `version`, `deletedAt` หากเลือก soft delete และ `placeholderFields:[{path,status}]` สำหรับการรับรองข้อมูลระดับฟิลด์

ใช้ unique index สำหรับ slug ของ news/sacred/categories; index ข่าวตาม publish/date และเนื้อหาเรียงลำดับตาม publish/sortOrder; categoryId index สำหรับ sacred; audit index ตาม entity/time และ TTL ตามนโยบายเก็บข้อมูลที่อนุมัติ ไม่ตั้ง TTL ของหลักฐานที่ต้องเก็บถาวรโดยอัตโนมัติ

ไม่ต้องสร้าง collection แยกสำหรับทุก repeater: variants, ความหมายตรา, เรื่องขอพร, ขั้นตอน และ contact topics เหมาะกับ embedded arrays เพราะแก้พร้อมเอกสารแม่และมีขนาดจำกัด Placeholders อาจคำนวณจาก metadata ร่วม; health เป็นผลตรวจ/รายงาน ไม่จำเป็นต้องเป็น collection ถาวรตั้งแต่แรก

ความสัมพันธ์ categories ต้องตรวจ referential integrity ใน application และกำหนดว่าลบหมวดที่มี sacred อ้างอิงจะห้ามลบหรือให้ย้ายหมวดก่อน

## 10. Cloudinary ที่เสนอ

ใช้ asset กลางใน `mediaAssets`: `publicId`, `assetId`, `resourceType`, `secureUrl`, `format`, `bytes`, `width`, `height`, `duration` สำหรับวิดีโอ, `legacyUrl/legacyId`, `originalFilename`, `createdAt` และ usage references ตามความจำเป็น เก็บ alt/caption/focal point ในระดับการใช้งานแต่ละเนื้อหา เพราะภาพเดียวอาจมีบริบทต่างกัน

กำหนด namespace ตามประเภท เช่น banners/news/sacred/gallery/team/about/videos; เก็บ original และสร้าง delivery transformations สำหรับ thumbnail/card/hero/OG โดยตรวจ syntax และข้อจำกัดตาม Cloudinary SDK ที่เลือกในช่วงพัฒนา

แบนเนอร์ต้องรักษา focalPoint แบบ normalized 0–1 และทดสอบ crop ทั้ง desktop/mobile; OG 1200×630; ทีมงาน 1:1; วัตถุมงคลและภาพข่าวไม่ควรบังคับ crop จนรายละเอียดหาย ใช้ responsive sizes และรักษา dimensions ลด layout shift

ให้อัปโหลดผ่านคำอนุญาตที่สร้างจากเซิร์ฟเวอร์หลังตรวจ session/role และ allowlist ประเภท ขนาด และปลายทาง ไม่ส่ง API secret ให้ browser ตรวจทั้ง client/server; gallery มี progress รายไฟล์และ retry; วิดีโอต้องคงเงื่อนไข 90 MB จนเจ้าของตกลงเปลี่ยน และรองรับ poster อัตโนมัติ/กำหนดเอง

ลบ content reference ก่อน แล้วตรวจว่า asset ยังถูกใช้ที่อื่นหรือไม่ จึงค่อยลบไฟล์ตาม retention ห้ามผูกการลบข่าวกับการทำลายภาพร่วมทันที ควรมี replace แบบ versioned และรายงาน orphan assets

## 11. แนวทาง Next.js / Auth.js / UI

แยกหน้าสาธารณะกับ admin layout ภายใต้ App Router ใช้ JavaScript และ Tailwind พร้อม component กลาง: ThaiField, CharCounter, MediaPicker, Repeater, PublicationControl, SEOFields และ PlaceholderBadge กำหนด schema/validation ร่วมให้เพดานและ required ตรงกัน

ทุกคำสั่งอ่านข้อมูลจำกัดสิทธิ์และเขียนข้อมูลต้องตรวจ session/role ฝั่งเซิร์ฟเวอร์ ไม่พึ่งเพียงการซ่อนปุ่ม กำหนด editor/admin และสิทธิ์อ่านข้อความแยกถ้าจำเป็น เลือกกลยุทธ์ Auth.js และ provider ก่อนออกแบบ auth collections ห้ามนำ password/session เดิมมาใช้โดยคัดลอกตรง ๆ และไม่บันทึกรหัสผ่าน token หรือ secret ลง audit diff

หลังเผยแพร่ให้ปรับ cache ของหน้าที่เกี่ยวข้องอย่างมีขอบเขต เช่น แก้ settings กระทบหลายหน้า แต่แก้ข่าวหนึ่งชิ้นกระทบหน้าข่าวนั้นและหน้ารวม เพิ่ม optimistic concurrency ด้วย version เพื่อเตือนเมื่อมีผู้แก้พร้อมกัน

## 12. Migration

1. ยืนยันแหล่งข้อมูลกับผู้ดูแลเดิม ขอ export เฉพาะ public content และไฟล์ต้นฉบับหากมี; การตรวจรอบนี้ยังไม่ได้รับหรือสร้าง export
2. ทำ inventory legacy ID, slug, publication, ordering, category mapping, metadata สื่อ และ placeholder paths ก่อนเขียน importer
3. ตรวจ category selector ที่ไม่มีตัวเลือก แยกปัญหาโหลด UI ออกจากข้อมูล foreign key ผิด ห้ามเดาความสัมพันธ์จากชื่ออย่างเดียว
4. ตรวจข้อมูลตัวอย่าง 32 จุด ให้เจ้าของรับรอง/แก้ก่อนเผยแพร่ รักษาธงไว้หากยังไม่ผ่าน และอย่าทำให้รายการตัวอย่างกลายเป็น “จริง” ระหว่างแปลงข้อมูล
5. ดาวน์โหลดสื่อที่ได้รับอนุญาตจากต้นฉบับ ตรวจ hash/deduplicate และสิทธิ์ใช้งาน นำเข้า Cloudinary พร้อม mapping old URL → new asset; ไม่ดาวน์โหลดสื่อใน audit รอบนี้
6. รักษา slug, เส้นทาง public, SEO, alt, date, ลำดับภาพ/รายการ, focal point และ OG ทำ redirect เมื่อ URL เปลี่ยน วันที่ข่าวเป็น date-only ไม่ควรเลื่อนวันจาก timezone
7. แปลงข้อความที่มี **ตัวหนา** และย่อหน้าอย่างคงความหมาย ไม่ตีความเป็น HTML ที่เชื่อถือได้โดยตรง
8. ย้าย singleton และ repeaters อย่างครบถ้วน กำหนด legacyId เพื่อให้ importer ทำซ้ำได้โดยไม่สร้างซ้ำ และทำ dry run/รายงาน mismatch
9. ไม่ย้ายรหัสผ่าน session หรือข้อมูลฟอร์มส่วนบุคคลเป็นค่าเริ่มต้น ข้อความติดต่อและ audit เก่าต้องมีขอบเขต/retention/การอนุญาตแยก หากจำเป็นจริง
10. เทียบจำนวนฐาน 3 ข่าว, 10 gallery, 4 banners, 5 sacred, 3 categories, 1 video record, 3 reviews, 6 FAQs, 2 team และ 2 singleton พร้อมตรวจสถานะเผยแพร่ เพราะจำนวนรายการไม่เท่ากับจำนวนที่ใช้แสดงจริง
11. ตรวจภาพ desktop/mobile, crop, broken links, ติดต่อ/LINE/maps, SEO, hidden sections และ permissions บน staging ก่อนกำหนดช่วง freeze และ final import เก็บ rollback ของข้อมูลและ asset mapping

| P2 | Soft delete/restore และ safe content export ที่แยก PII | เพิ่มการกู้คืนและย้ายข้อมูลในอนาคต; ยังไม่ยืนยันว่าระบบเดิมมี |

ภาพรวม UI เดิมใช้ Sidebar สีน้ำเงินเข้ม/ทอง พื้นหลังอ่อนและการ์ดทางลัด อ่านง่าย แต่ Sidebar ยาวจนต้องเลื่อน Dashboard มีพื้นที่ว่างมาก สามารถเพิ่มรายการ “สิ่งที่ต้องทำ” จาก health/placeholder และ publication summary ได้โดยไม่เพิ่มความซับซ้อน

## 14. สิ่งที่ยังต้องยืนยันก่อนเริ่มพัฒนา

- ช่องหมวดหมู่ไม่โหลดเพราะข้อมูล publish/filter, mapping หรือข้อผิดพลาด UI/API
- schema และ workflow ของ contact messages เมื่อมีข้อมูลจริง โดยใช้ตัวอย่างสังเคราะห์ที่ไม่มี PII
- bulk actions, pagination เมื่อข้อมูลมาก, delete recovery/cascade และสิทธิ์แต่ละคำสั่ง
- validation ภาพจริง, upload limits, crop behavior, batch metadata และการกำจัดไฟล์เก่า
- มี export ต้นฉบับหรือเข้าถึงข้อมูลโดยผู้พัฒนาระบบเดิมอย่างเป็นทางการได้หรือไม่
- ประวัติเป็น audit log อย่างเดียวหรือมี snapshot/restore นอก UI ที่ตรวจ
- ผู้ดูแลมีกี่บัญชี ต้องการ role/2FA/ผู้อนุมัติหรือไม่ และจะเลือก provider ของ Auth.js แบบใด

รายการข้างต้นเป็นช่องว่างหลักฐาน ไม่ใช่การยืนยันว่าระบบเดิมไม่มีคุณสมบัติเหล่านั้น รายงานนี้เพียงพอเป็นฐาน requirements และ data model ฉบับแรก โดยให้แก้ category mapping และรับรองข้อมูลตัวอย่างก่อนกำหนด migration จริง
